1. Chronological narrative: the three pivots

Three pivots shaped this project, each forced by something concrete (storage, a losing init, a compute-allocation goal), not by taste. docs/PLAN.md has the blow-by-blow; this is the condensed why, in order.

1.1 REAL-Colon → HyperKvasir (2026-09-03)

The original eval target was REAL-Colon (946 GB). Both DSS containers for project pr74ze were already full (pr74ze-dss-0001 at 199/200 GB, pr74ze-dss-0000 over quota) — there was nowhere to put it. GastroNet-5M (the intended SSL corpus) also turned out not to be on HuggingFace despite an initial assumption; it lives behind a data-use agreement on cortex.thetavision.nl ("the portal"), which I had authorisation for. HyperKvasir was already staged read-only on DSS (pr74ze-dss-0001/ra82sat2/zeiss_data), so it became the eval set: zero-shot on hkv_findings (23-way, later 20-way after taxonomy cleanup), hkv_category (4-way), hkv_tract (2-way, upper vs lower GI), hkv_pathology (2-way), plus hkv_seg (zero-shot polyp segmentation, dense-feature k-NN label transfer on 1000 mask pairs). vlfz/data/realcolon.py was kept, unused, dormant code — not deleted, in case storage ever frees up.

1.2 Four settings → two settings: SigLIP-2 dropped (2026-09-16)

The original design compared two SSL objectives (LeJEPA, DINO v1) crossed with two backbone inits (SigLIP-2, ImageNet ViT-B/16) — four settings. The first complete 4-setting result (on a curated ~581k-image / 12% subset of GastroNet-5M) showed SigLIP-2 losing to ImageNet on every pre-SSL task, and LeJEPA/ImageNet regressing severely post-SSL. Given that, and wanting a fair comparison against a teammate’s ImageNet-init pipeline (lilian70nn/Endoscopy), the decision was to drop SigLIP-2 entirely and put all compute into ImageNet-init LeJEPA vs DINO. This halved the SSL matrix from four settings to two. SigLIP-2 code paths (vlfz/models/vit_backbone.py’s VALID_INITS, load_weights.py’s openclip_siglip2_trunk, the choices=["siglip2","imagenet"] CLI flags) were left in place, dormant, same pattern as REAL-Colon — only the default init and the sweep loops changed.

1.3 Curated 12% subset → the full ~4.9M-image raw corpus, streamed (2026-09-16 → 09-22)

The subset run above was explicitly provisional: 60 shards / 581k images out of GastroNet-5M’s full ~4.9M. The stated end goal was always a durable foundation-model checkpoint, and a checkpoint trained on 12% of the available unlabeled corpus is a weaker artifact than one need be. The original curated-ingest plan (portal_to_wds.py: download a portal zip, resize to 224px, JPEG re-encode, phash-dedup, write into permanent .tar WebDataset shards, delete the raw zip) produces a compact ∼68 GB tier for all 506 archives — but that ingest itself is a multi-hour-per-batch background job with its own failure surface (see 22df058 below), and re-encoding pixels once throws away information a from-scratch SSL run doesn’t need to lose.

Comparing directly against the teammate’s cortex_dataloader.py (fetched and read) settled it: her approach streams a zip, decodes straight from the raw zip bytes at full resolution, yields, deletes, moves to the next zip — no local curation step at all. vlfz/data/portal.py (916a684 onward) is the from-scratch equivalent of that: a resumable, bounded-disk, checkpoint-safe iterable stream directly over the 506 raw portal zips, no permanent local copy of the corpus at all. This is what the codebase calls "fullstream." Section 4 below walks through it end to end.

Two secondary decisions from the same session, recorded so they don’t get re-litigated: multi-GPU (--gres=gpu:2/4) was investigated and explicitly not pursued — DINO’s teacher-output centering (update_center in dino_lib.py) batch-means locally with no dist.all_reduce, and LeJEPA’s SIGReg term is a per-batch distribution statistic; under naive DDP each rank would silently compute a different center / a noisier regularizer estimate than intended, and fixing that correctly was judged its own sub-project not worth the schedule risk. And GastroNet-5M EDA was explicitly deferred until the full corpus finished ingesting, rather than doing a partial pass now and a redo later.

2. Debugging war stories

In chronological order. Each entry: what broke, how it surfaced, the actual fix, why the fix works. These are the bugs that actually cost wall-clock time or silently corrupted a result — not every commit, just the ones worth remembering the shape of.

The frozen global_step / dead first full runccb8985silent failure

Symptom. The first full LeJEPA/ImageNet SSL run "completed" — no crash, no error — but TensorBoard showed lr flat at exactly 0.0 and loss flat at 0.737 across 10k logged steps. It had trained on nothing.

Root cause, two independent bugs stacked:

  1. training_step called opt.optimizer.step() — the raw torch.optim.AdamW.step() — instead of opt.step() (the LightningOptimizer wrapper that routes through Strategy.optimizer_step). This had been a deliberate workaround for an intermittent CPU-login-node hang around the optimizer step, kept as a blanket "defense in depth" measure. But bypassing LightningOptimizer means trainer.global_step never increments. cosine_lr(global_step=...) then never leaves warmup step 0, so every param group’s LR is scaled by 0 forever. Nothing learns.
  2. Separately, ModelCheckpoint(every_n_train_steps=...) also keys off global_step — so with (1) in place, no last.ckpt or periodic checkpoint was ever written either. A crash would have lost everything, not just resumed from a stale point.
  3. A third, independent bug in the same commit: webdataset_loader called ds.with_epoch(steps_per_epoch) on the WebDataset pipeline before the DataLoader fan-out across workers. With num_workers=N, the entire dataset pipeline runs inside every worker process, so with_epoch(k) yields N·k batches per Lightning epoch, not k. At N=12 that turned a nominal epoch into ~56k batches (~5h) — long enough that on_train_epoch_end (the other place a checkpoint could fire) never ran within the wall-clock budget either.

Fix (commit ccb8985). Route through opt.step() whenever CUDA is available (the raw bypass is now CPU-smoke-only, where the original hang was actually observed and GPU never reproduced it). And apply .with_epoch() on the WebLoader object, which sits after the multiprocessing fan-in, so it bounds the combined stream rather than each worker’s private copy of it. Verified post-fix: requesting 40 batches yields exactly 40, stable across epochs, at num_workers=4.

Why this matters for reading old results: any result recorded before ccb8985 landed (2026-09-08) from a full-stage run is suspect by construction — the model literally could not have moved.

TIMEOUT vs. clean exit: the self-resubmit that only fired half the timec0be0e6SLURM

Symptom. Two 3-epoch SSL runs (LeJEPA/ImageNet, DINO/SigLIP-2) landed on lrz-hgx-h100-003, a node running at 0.23 it/s — roughly 11× slower than a healthy A100 (2.65 it/s). Both hit the then-6h wall at epoch 1 and simply stopped. No resubmit happened.

Root cause. The original sbatch script’s resubmit logic was a trailing shell block after the python -m vlfz.ssl.pretrain line: if [ -f DONE ]; then ...; else sbatch $0; fi. That only executes on a clean process exit. A SLURM wall-time TIMEOUT sends SIGTERM/SIGKILL straight to the python process; the shell script’s own line is killed with it, so the trailing resubmit code never runs. "Self-resubmitting" was true only for failures the process itself chose to exit from, not for the actual timeout case it existed to handle.

Fix (commit c0be0e6). Move the resubmit logic into a trap finish EXIT handler, which fires on any shell exit path, TIMEOUT included — paired with #SBATCH --signal=B:TERM@180, which asks SLURM to deliver SIGTERM 3 minutes before the hard kill so the trap has time to run and decide whether to resubmit (only if last.ckpt exists, i.e. forward progress was actually made; otherwise it’s left for inspection rather than resubmitted blindly). The degraded node was also excluded via --exclude=lrz-hgx-h100-003 until fixed.

This exact asymmetry resurfaced during the full-corpus phase (see §3 below, job 5808423): a LeJEPA fullstream job hit the hard 48h SLURM TIMEOUT and did not self-resubmit, requiring a manual sbatch afterwards, even though lrz/sbatch_fullstream.sbatch uses the equivalent trap-based mechanism (trap '...kill -USR1 "$child"...' USR1 plus #SBATCH --signal=B:USR1@300). The companion DINO job resubmitted itself cleanly on the same kind of wall-time exhaustion. I did not fully root-cause why LeJEPA’s trap didn’t fire that particular time — noting this honestly rather than inventing an explanation; see §3.4.

Resume re-running a fresh N epochs instead of continuing from global_stepf898184

Symptom. LeJEPA/ImageNet (job 5776887) TIMEOUT’d at 1 epoch, resumed as 5778010, and ended up doing ~3 more epochs on top — final global_step ~18561 (~4 epochs) against the intended 14061 (3 epochs), while the other three settings in the same 4-way comparison got exactly 3.

Root cause. The trainer was configured with max_epochs=epochs. On resume from last.ckpt, Lightning correctly restores trainer.global_step, but the WebDataset-backed iterable dataloader’s own epoch counter is not part of that checkpoint state and resets to 0. So max_epochs=3 after a resume means "3 more epochs from here," not "3 epochs total."

Fix (commit f898184). Bound training on an absolute step count instead: max_epochs=-1, max_steps=(args.limit_steps or total_steps), where total_steps = epochs * steps_per_epoch is computed once up front. "3 epochs" now means exactly 3 × steps_per_epoch optimizer steps, regardless of how many separate SLURM allocations that took to accumulate. The already-overrun LeJEPA/ImageNet run from before this fix was not silently kept — it’s flagged as a ~4-epoch outlier in the results rather than presented as comparable.

Symptom. A DINO/SigLIP-2 resume (job 5778011) died with OSError: [Errno 28] No space left on device partway through writing a checkpoint. Separately, a dense crash-loop on 2026-09-14 (job IDs 5788346 onward, ~4 minutes apart, dozens of FAILED attempts) hit the same wall repeatedly — confirmed directly from lrz/logs/vlfz_ssl_5788346.err, which ends in:

  • e7f9df3: after a run reaches DONE, delete last.ckpt and every ckpt-*.ckpt in its output directory, keeping only ema_backbone.pt + the TensorBoard log dir + the DONE flag. See the code excerpt in §4.3.

The full-corpus ("fullstream") phase later moved outputs to a real home directory again ($HOME/vlf_zeiss_fullstream, deliberately not the historical vlf_zeiss_runs symlink) with its own explicit preflight quota check before training starts (fullstream.py::preflight, §4.2) — a direct, permanent response to having been burned by this exact failure mode twice.

Corrupt / truncated portal images: three iterations to the final design916a68422df05884a6d1626c315e

This bug went through three distinct designs before settling. Worth keeping all three in mind, since the final shape only makes sense in light of what the first two got wrong.

Iteration 1 — crash (discovered the hard way)

DINO’s full fullstream run died 8500 steps in on an uncaught OSError: image file is truncated, raised from inside PortalStream.decode with no guard at all. Confirmed directly in full_dino.log:

$HOME/vlf_zeiss_fullstream/full_dino.log (real traceback, step ~8583, job 5799991/5799992-era)
File ".../vlfz/data/portal.py", line 52, in _worker_sample
    return _transform_sample(*task, _worker_transform)
  File ".../vlfz/data/portal.py", line 45, in _transform_sample
    return transform(PortalStream.decode(raw))
  File ".../vlfz/data/portal.py", line 393, in decode
    return im.convert('RGB')
  File ".../PIL/ImageFile.py", line 399, in load
    raise OSError(msg) from e
OSError: image file is truncated

Separately, the same failure class already existed in the (older, curation-based) ingest path (pipeline/ingest/portal_to_wds.py): one corrupt zip raised an uncaught zipfile.BadZipFile and killed a multi-hour backfill at shard 69/506 (commit 22df058) — fixed there by catching, logging to _failed.txt, and continuing without marking the shard done (so a later backfill retries it).

Iteration 2 — bounded skip rate (84a6d16)

916a684’s first fix for the streaming path was an unconditional skip: catch, log, drop the sample, move on. That silently diverged from docs/FULLSTREAM.md’s documented policy ("corrupt images stop execution") without saying so anywhere. 84a6d16 replaced it with a bounded tolerance: skip and count via PortalStream.attempts/failures, but hard-fail if the failure rate exceeds portal_max_failure_rate (default 0.1%) once at least portal_failure_min_sample (default 1000) images have been attempted. The reasoning at the time: neither "one bad image kills a 3-day run" nor "silently lose an unknown amount of data forever" was acceptable, so bound the loss instead of picking one of those two failure modes.

Iteration 3 — always blank, never drop (26c315e, final)

The bounded-skip design worked but complicated __iter__’s batch-accumulation loop (a dropped sample means the batch can come up short, which interacts with exact-cardinality resume). A simpler redesign replaced skip-and-count with always replace with a deterministic blank sample — PortalStream.decode now never raises: a truncated image that PIL’s ImageFile.LOAD_TRUNCATED_IMAGES = True cannot recover, or a completely missing archive member (raw=None, a real KeyError from extraction), both become Image.new('RGB', (224, 224)). This is strictly better for the property that actually matters for checkpoint-resume correctness: self.sizes (the per-batch sample counts) and the cursor stay exactly right regardless of how many images were bad, so resume never has to reconcile a shifted batch boundary. The bounded-failure-rate machinery from iteration 2 (now fully dead code — nothing produces None for it to gate) was removed outright rather than left dormant, since it was actively wrong by this point, not just unused. attempts/failures remain as plain telemetry via coverage(), persisted across resumes.

Final measured impact: 0 decode failures across all 13,383,770 decode attempts on the winning DINO run (see §6) — the corpus, once actually swept in full, turned out to be clean; the machinery exists for the tail risk, not because it fired often.

Portal HTTP 5xx outage: url() never retried, only download() did3b7b3a4

Symptom. An ~2-hour window of the portal returning HTTP 500 killed both training jobs on 2026-09-24. Confirmed in full_dino.log:

$HOME/vlf_zeiss_fullstream/full_dino.log (real traceback, jobs 5801249/5802400-era)
File ".../vlfz/data/portal.py", line 145, in download
    with requests.get(self.url(item), headers={'Range': f'bytes={have}-'},
  File ".../vlfz/data/portal.py", line 118, in url
    raise RuntimeError(f'Portal authorization/request failed: HTTP {r.status_code}')
RuntimeError: Portal authorization/request failed: HTTP 500

Root cause. PortalClient.download() already retried transient failures with exponential backoff (up to 6 attempts). But download() gets the actual signed download URL by calling self.url(item) first, and url() itself had no retry logic at all — any non-200, non-401/403 response (including a 500 from the portal’s own infrastructure, nothing to do with this client) was immediately fatal. download()’s retry loop was retrying a call that itself never gave the outage a chance to pass.

Fix, two commits, landed 40 minutes apart.

  • 26c315e gave url() its first retry loop: up to 6 attempts, exponential backoff capped at 30s, 401/403 still renews the session once first. Total budget: under a minute.
  • 3b7b3a4, the very next commit, found that budget insufficient against the actual outage duration and rewrote it: a 3-hour deadline (comfortably past the observed 2-hour outage), backoff ramping to a 5-minute cap instead of 30s, and retrying network exceptions (requests.RequestException, e.g. a connection reset) the same way as a 5xx status, not just HTTP-level failures. The reasoning, from the code comment: retrying costs nothing since the GPU allocation is already held either way, while dying costs however long it takes a human to notice plus re-entering a queue that has taken up to 2 days under real contention — so budget for hours, not seconds. Any non-5xx, non-401/403 status (404, 400, ...) is still immediately fatal: that’s a real, permanent problem, and retrying it forever would only hide it.

See §4.1 for the actual url() code as it stands after both fixes.

3.4 Chronological failure narrative

One entry per distinct failure mode actually observed in the full-corpus phase, in the order they were hit. 3.4.1 — Manifest-indexing BadZipFile (job 5795331, 2026-09-17)

The very first fullstream submission failed in 13 minutes — too fast to be a training crash, and indeed it was in index_manifest() (§4.1), which runs once up front to build the frozen 506-archive manifest before any training starts. The corresponding pilot log shows the real exception:

$HOME/vlf_zeiss_fullstream/pilot_dino.log (real traceback)
File ".../zipfile.py", line ..., in _RealGetContents
    raise BadZipFile("File is not a zip file")
zipfile.BadZipFile: File is not a zip file

i.e. a specific portal archive was, at that moment, not readable as a zip at all — a genuinely bad or still-being-written archive on the portal side, encountered during the manifest-build pass (index_manifest’s fallback path: try a streamed RangeReader open first, and if that raises, fully download and retry via archive_members — the traceback shown means even the full download+retry path hit the same unreadable archive). This predates and is not the same code path as the later truncated-image-inside-a-good-zip bug (3.4.2); this is a whole archive being bad. Honest gap: I did not find a dedicated commit that hardens index_manifest itself against this — the run simply succeeded on the next attempt (5795712), consistent with a transient portal-side hiccup on one archive rather than a permanently broken one, but that is an inference from the retry succeeding, not a confirmed root cause.

3.4.4 — The recurring TIMEOUT/resubmit asymmetry, still not fully explained (job 5808423, 2026-09-24/26)

5808423 (LeJEPA’s full run) hit the hard 48-hour SLURM wall (State=TIMEOUT, Elapsed=2-00:00:19, i.e. it ran essentially the full 48h ceiling) and did not self-resubmit, requiring a manual sbatch lrz/sbatch_fullstream.sbatch afterwards. Its DINO counterpart, 5808422, finished the same wall-time window as a clean COMPLETED exit (1-23:58:10, i.e. it happened to land just under the wall and exit via the normal DONE path rather than being timed out at all) — so this particular pair does not actually demonstrate the trap failing under equal conditions; DINO simply didn’t need the trap that time. The trap mechanism itself (lrz/sbatch_fullstream.sbatch’s trap '...kill -USR1 "$child"...' USR1 plus #SBATCH --signal=B:USR1@300, giving 5 minutes’ notice) is the same one described fixed in §2 (c0be0e6) for the earlier subset-era jobs, and reads correctly on inspection (§4.5). Whether 5808423’s non-resubmit was a genuine recurrence of the TIMEOUT/clean-exit asymmetry, a SIGUSR1-forwarding race specific to that job, or something else entirely was not root-caused — I am flagging it honestly as an open question rather than asserting a cause I cannot back with log evidence. Operationally, training resumed the same day via manual resubmission and LeJEPA reached DONE normally afterward (evaluation completed 2026-09-27, per evaluation_lejepa.json).

def _transform_sample(raw, identity, transform):
    import torch
    import numpy as np
    # PortalStream.decode already turns a truncated/corrupt image, or a
    # missing archive member (raw=None), into a deterministic blank -- it
    # never raises, so there's nothing to catch here.
    seed = int.from_bytes(hashlib.sha256(identity.encode()).digest()[:4], 'big')
    py_state, np_state = random.getstate(), np.random.get_state()

        random.seed(seed)
        np.random.seed(seed)
        try:
            return transform(PortalStream.decode(raw))
        finally:
            random.setstate(py_state)
            np.random.set_state(np_state)

class PortalStream(IterableDataset):
    """Iterable batch source. Call commit only after a successful optimizer step.

    A corrupt/truncated image, or an archive member the manifest lists but
    the archive no longer has, is replaced with a deterministic blank sample
    rather than dropped or raised -- see PortalStream.decode. That keeps
    self.sizes/cursor exact regardless of corruption, so checkpoint resume
    never has to reconcile a shifted batch boundary. attempts/failures are
    informational telemetry only (surfaced via coverage()), not a gate --
    persisted across resumes via state_dict/load_state_dict so counts stay
    accurate for the whole run, not just one epoch or one allocation.
    """
    def __init__(self, client, cache, manifest, transform, collate, batch_size=128, seed=0, epochs=3,
                 transform_workers=0):
        self.client, self.cache, self.manifest = client, cache, manifest
        self.transform, self.collate = transform, collate
        self.seed, self.epochs = seed, epochs
        self.transform_workers = transform_workers
        self.sizes = batch_sizes(sum(len(a['members']) for a in manifest['archives']), batch_size)
        self.cursor = {'epoch': 0, 'batch': 0}
        # Live counts advance as samples are produced; _committed is the
        # snapshot state_dict()/checkpointing sees -- frozen between commits,
        # exactly like self.cursor, so a crash between producing and
        # committing a batch doesn't change what a resume sees.
        self.attempts = 0
        self.failures = 0
        self._committed = {'attempts': 0, 'failures': 0}

    def state_dict(self):
        return {**self.cursor, 'fingerprint': self.manifest['fingerprint'], **self._committed}

PortalStream’s own docstring (kept in full here, since it’s the clearest single statement of the resume-correctness invariant in the file) explains why a corrupt image is blanked rather than dropped: dropping would change self.sizes (the per-batch counts, computed once from the manifest) and shift every later batch boundary, which would make an exact checkpoint resume impossible to reason about. attempts/failures are tracked as two separate counters — a live one that advances immediately as samples are produced, and a _committed snapshot that only moves inside commit() — for the same reason self.cursor itself is snapshotted that way: a crash between producing a batch and committing it must not be able to corrupt what the next resume trusts.

__iter__ is the actual streaming loop. A few things worth pointing out that are easy to miss on a first read:

  • Two-archive lookahead. pair = order[ai:ai+2] reserves cache space for the current archive and prefetches the next one on a background thread (downloads.submit(...)) while the current one is being processed — the single-threaded prefetch stays ahead of decode as long as archive processing (measured ~60s) is slower than the download (measured ~38s at the tuned worker count; see the throughput comment in §5.2).
  • Resume skip logic. skip = sum(self.sizes[:batch_start]) converts a checkpointed (epoch, batch) cursor back into "how many images into this shuffled archive order do I need to fast-forward" — deterministic because archive order and per-archive member order are both reproduced from the same seeded random.Random calls used originally.
  • Cache eviction. path.unlink() at the very end of each archive’s loop body deletes the local copy immediately after it’s fully consumed — the two-archive budget is enforced by never holding more than the current + one prefetched archive on disk at once.
  • Process-pool transforms. When transform_workers > 0, augmentation runs in a ProcessPoolExecutor (not threads — PIL/augmentation work is CPU-bound and would serialize under the GIL) seeded via _init_transform_worker, with the parent process retaining sole ownership of the stream/cursor state.

4.2 vlfz/ssl/fullstream.py — the orchestrator

  • preflight(root) runs before anything else: it waits up to 90s for CUDA to become visible (a fresh allocation can briefly report no GPU while NVML initializes — not worth discarding a 48h allocation over), refuses to run if OUT_ROOT is a symlink or not a direct child of $HOME (a direct, permanent guard against ever repeating the historical vlf_zeiss_runs-symlink-onto-scratch confusion from §2/WS4), and does a real mmlsquota check plus an actual 1 MB write-and-fsync probe before training starts — checking the quota banner was already established as untrustworthy earlier in the project (docs/PLAN.md’s 2026-09-14 notes record the LRZ quota dashboard not moving after real deletions), so this checks the filesystem directly.

def llrd_param_groups(backbone, other_params, base_lr, decay):
    blocks = backbone.trunk.blocks
    depth = len(blocks)
    groups, seen = [], set()

    def add(params, scale):
        ps = [p for p in params if p.requires_grad and id(p) not in seen]
        for p in ps:
            seen.add(id(p))
        if ps:
            groups.append({"params": ps, "lr": base_lr * scale})

    add(other_params, 1.0)
    add([p for n, p in backbone.trunk.named_parameters()
         if n.startswith(("patch_embed", "pos_embed", "cls_token", "reg_token"))],
        decay ** (depth + 1))
    for i, blk in enumerate(blocks):
        add(list(blk.parameters()), decay ** (depth - i))
    add([p for n, p in backbone.trunk.named_parameters()
         if n.startswith(("norm", "fc_norm", "head", "attn_pool"))], 1.0)
    add(backbone.trunk.parameters(), decay ** (depth + 1))  # any stragglers
    return groups

llrd_param_groups builds the layer-wise-LR-decay optimizer groups: the backbone’s transformer blocks each get their own param group scaled by decay ** (depth - i) (deeper blocks — closer to the output — get a higher effective LR, shallower/earlier blocks get decayed further toward zero, the standard LLRD scheme for fine-tuning pretrained transformers). The seen/add() bookkeeping exists purely to guarantee every parameter lands in exactly one group — important because torch.optim.AdamW silently double-updates a parameter that appears in two groups, which would be a very quiet bug to have shipped.

"""LeJEPA objective (Balestriero & LeCun 2025, arXiv:2511.08544).

    loss = prediction_loss + sigreg_lambda * SIGReg + var_weight * variance_hinge

- prediction_loss : two augmented views embedded by the SAME encoder (no EMA
  teacher). A small predictor maps view A's embedding toward view B's, and
  symmetrically. The TARGET is stop-gradient'd so the invariance term cannot be
  minimised by shrinking embeddings toward a constant.

- SIGReg (Sketched Isotropic Gaussian Regularization) : project the standardized
  batch onto many random 1-D directions and push each 1-D marginal toward a
  standard Gaussian via the Epps-Pulley characteristic-function test. By
  Cramer-Wold, matching all 1-D projections matches the full isotropic Gaussian.
  Cost is linear in dim and batch. Vectorized over slices/frequencies.

- variance_hinge : an explicit, numerically-stable VICReg-style floor on
  per-feature std (belt-and-braces anti-collapse; SIGReg shapes, this guards).
"""
from __future__ import annotations

import torch
import torch.nn.functional as F


def _standardize(z: torch.Tensor, eps: float = 1e-3) -> torch.Tensor:
    std = z.std(dim=0, keepdim=True).clamp_min(eps)
    return (z - z.mean(dim=0, keepdim=True)) / std


def variance_hinge(z: torch.Tensor, target_std: float = 1.0, eps: float = 1e-4) -> torch.Tensor:
    std = torch.sqrt(z.var(dim=0) + eps)
    return torch.relu(target_std - std).mean()


def sigreg(z: torch.Tensor, n_slices: int = 256, n_freq: int = 16,
          freq_max: float = 5.0) -> torch.Tensor:
    """Sketched Isotropic Gaussian Regularization. 0 iff every sampled 1-D
    projection of the standardized batch looks standard-Gaussian."""
    N, D = z.shape
    zc = _standardize(z)
    dirs = torch.randn(D, n_slices, device=z.device, dtype=z.dtype)
    dirs = dirs / (dirs.norm(dim=0, keepdim=True) + 1e-8)
    proj = zc @ dirs                                            # (N, S)
    ts = torch.linspace(0.1, freq_max, n_freq, device=z.device, dtype=z.dtype)
    tx = proj[:, :, None] * ts[None, None, :]                   # (N, S, T)
    ecf_re = torch.cos(tx).mean(dim=0)                          # (S, T)
    ecf_im = torch.sin(tx).mean(dim=0)                          # (S, T)
    cf_re = torch.exp(-0.5 * ts ** 2)[None, :]                  # std-normal CF (real)
    weight = torch.exp(-0.5 * ts ** 2)[None, :]                 # Gaussian integration weight
    diff = (ecf_re - cf_re) ** 2 + ecf_im ** 2
    return (diff * weight).mean()


def prediction_loss(emb_a: torch.Tensor, emb_b: torch.Tensor, predictor) -> torch.Tensor:
    pa = predictor(emb_a)
    pb = predictor(emb_b)
    return 0.5 * (
        F.smooth_l1_loss(pa, emb_b.detach()) + F.smooth_l1_loss(pb, emb_a.detach())
    )


def lejepa_loss(emb_a, emb_b, predictor, *, sigreg_lambda=1.0, var_weight=1.0,
                n_slices=256, n_freq=16):
    pred = prediction_loss(emb_a, emb_b, predictor)
    reg = 0.5 * (sigreg(emb_a, n_slices, n_freq) + sigreg(emb_b, n_slices, n_freq))
    var = 0.5 * (variance_hinge(emb_a) + variance_hinge(emb_b))
    total = pred + sigreg_lambda * reg + var_weight * var
    return total, {"pred": float(pred.detach()), "sigreg": float(reg.detach()),
                   "var": float(var.detach())}


@torch.no_grad()
def effective_rank(z: torch.Tensor) -> float:
    """Collapse proxy: exp(entropy of normalized singular values). Full rank -> ~D."""
    z = z - z.mean(0, keepdim=True)
    s = torch.linalg.svdvals(z.float())
    p = s / s.sum().clamp_min(1e-12)
    return float(torch.exp(-(p * (p.clamp_min(1e-12)).log()).sum()))

LeJEPA (Balestriero & LeCun 2025) has no EMA teacher at all — both augmented views go through the same encoder, and collapse is prevented by two explicit regularizers instead of an asymmetric architecture. prediction_loss is the JEPA part: a small predictor maps one view’s embedding toward the other’s, symmetrically, with the target always .detach()’d so the invariance term can’t be trivially minimized by collapsing both embeddings to a constant. sigreg (SIGReg — Sketched Isotropic Gaussian Regularization) is the more novel piece: it projects the standardized batch onto n_slices random 1-D directions and, for each, compares the empirical characteristic function against a standard Gaussian’s via the Epps-Pulley test (ecf_re/ecf_im vs. the closed-form Gaussian CF cf_re, weighted by a Gaussian kernel in frequency). By the Cramer-Wold theorem, matching every 1-D projection’s distribution is equivalent to matching the full isotropic Gaussian in the original space — and because it’s computed over random projections rather than the full covariance structure, cost stays linear in both batch size and embedding dimension. variance_hinge is a simpler VICReg-style floor on per-feature standard deviation, kept as an explicit "belt and braces" anti-collapse guard on top of what SIGReg already provides shape-wise. effective_rank (exponentiated entropy of the normalized singular-value spectrum of a feature batch) is the collapse-monitoring metric logged every epoch as collapse/effective_rank — this is what the selection gate in §6 checks did not collapse for either setting.

vlfz/ssl/dino_lib.py
"""DINO v1 self-distillation objective + schedules (Caron et al. 2021).

A student matches an EMA teacher's sharpened, centered output distribution across
multiple augmented crops of the same image (2 global + n_local). No labels, no
negatives; centering + teacher sharpening prevent collapse.
"""
from __future__ import annotations

import math

import torch
import torch.nn.functional as F


def dino_loss(
        student_out: list[torch.Tensor], 
        teacher_out: list[torch.Tensor],
        center: torch.Tensor, 
        student_temp: float, 
        teacher_temp: float
) -> torch.Tensor:
    """student_out: over ALL crops; teacher_out: over the 2 GLOBAL crops. CE of
    every student crop vs every teacher crop, skipping the identical view."""
    t = [F.softmax((tt - center) / teacher_temp, dim=-1).detach() for tt in teacher_out]
    total, n = 0.0, 0
    for ti, tq in enumerate(t):
        for si, sq in enumerate(student_out):
            if si == ti:
                continue
            total = total + (-(tq * F.log_softmax(sq / student_temp, dim=-1)).sum(-1).mean())
            n += 1
    return total / max(1, n)






@torch.no_grad()
def update_center(center: torch.Tensor, teacher_out: list[torch.Tensor],
                 momentum: float) -> torch.Tensor:
    batch_center = torch.cat(teacher_out, dim=0).mean(dim=0)
    center.mul_(momentum).add_(batch_center, alpha=1.0 - momentum)
    return center






def cosine_lr(step: int, total: int, base_lr: float, min_lr: float, warmup: int) -> float:
    if step < warmup:
        return base_lr * step / max(1, warmup)
    p = (step - warmup) / max(1, total - warmup)
    return min_lr + 0.5 * (base_lr - min_lr) * (1 + math.cos(math.pi * p))






def teacher_temp_at(step: int, total: int, t0: float, t1: float, warmup_frac: float) -> float:
    frac = step / max(1, total)
    return t0 + (t1 - t0) * min(1.0, frac / max(1e-6, warmup_frac))

DINO v1 (Caron et al. 2021) is the more classical self-distillation setup: a student matches an EMA teacher’s sharpened, centered output distribution across every augmented crop (2 global + several local) except a crop matched against itself. dino_loss’s double loop explicitly skips si == ti — the identical-view pair — since matching a view against its own teacher output trivially would leak no learning signal and would also make the temperature-controlled sharpening term degenerate. update_center is the other collapse-prevention mechanism, alongside teacher sharpening: an EMA-averaged running mean of teacher outputs is subtracted before softmax, which stops the teacher from collapsing to a single/near-constant output distribution — this is exactly the term flagged in docs/PLAN.md as the reason multi-GPU DDP was not pursued (§1.3): it batch-means locally with no cross-rank reduction, so naive DDP would let each rank drift to its own center. teacher_temp_at linearly warms the teacher’s softmax temperature from t0 to a lower, sharper t1 over the first warmup_frac of training — starting soft (easier for the student to match early) and sharpening over time (forcing more confident, more discriminative teacher targets as training progresses).

The self-resubmission mechanism in full. #SBATCH --signal=B:USR1@300 asks SLURM to deliver SIGUSR1 5 minutes before the hard wall-time kill; the trap forwards it to the Python child (kill -USR1 "$child"), which PortalWalltime (§4.3) turns into a synchronous checkpoint save and SystemExit(75). The wait "$child"; ... if kill -0 "$child"; then wait "$child"; fi double-wait handles a real shell race: a signal delivered to the shell can interrupt the first wait before the child has actually exited, so it re-waits if the child is still alive. rc = 75 triggers exactly one more sbatch of this same script, capped at STREAM_RESUMES < 100 as a sanity ceiling against an infinite resubmit loop; any other non-zero exit code is treated as a real failure and left for inspection rather than auto-retried — this is the distinction discussed at length in §2 (c0be0e6): a checkpointed, intentional wall-time exit resubmits, everything else does not. --time=48:00:00 is the value c26aefe raised from 24h, specifically because queue wait (not resubmit overhead) dominated total time-to-completion — getting one allocation pair admitted took roughly 2 days against ~550 cluster-wide pending jobs on these partitions at the time, so halving the number of 24h-boundary re-entries into that queue was the actual lever, not making each individual run faster.

5.4 Foundation-model selection rule and promotion

The rule, as stated in CARD.json (written verbatim by the promotion step, quoted here rather than paraphrased): primary criterion is mean post-SSL balanced-accuracy across the 4 HyperKvasir classification tasks plus Dice on hkv_seg; ECE/NLL and effective-rank are a gate, not the ranking — any regression vs. the shared pre-SSL ImageNet baseline on the primary metric, or an effective-rank collapse, disqualifies a candidate regardless of any other metric looking good. This was decided deliberately in favor of discriminative quality over calibration for a foundation checkpoint specifically because downstream fine-tuning recalibrates anyway — ECE/NLL matter for the zero-shot comparison this benchmark is actually about, but not for judging what’s worth carrying forward as a base for further training.

Promotion itself (triggered manually once both settings’ evaluation_*.json receipts existed) copies the winning setting’s ema_backbone.pt to a separate $OUT_ROOT/foundation_model/ema_backbone.pt, writes the CARD.json provenance card recording both settings’ full metrics (so the decision stays auditable, not just the winner’s numbers in isolation), and logs the same file as a versioned W&B Artifact (dino-imagenet-s506-raw-e3) via the block at the end of fullstream.py (§4.2) — specifically so the one file every future downstream fine-tuning run depends on does not live only on LRZ storage, whose reliability this project had already been burned by twice (§2/WS4, §3.4.1–3.4.3).
