PART 1
Achievements

What is built

The experiment is a clean before/after loop. For each of four model settings — {LeJEPA, DINO v1} × {SigLIP-2 ViT-B/16 init, ImageNet ViT-B/16 init} — measure zero-shot calibration on HyperKvasir, then repeat after in-domain self-supervised pretraining on GastroNet-5M, and report the change in ECE and NLL. “Zero-shot” means a weighted k-NN on frozen features (DINO protocol, k = 20, τ = 0.07); these backbones are vision-only, so there is no text head.

Five downstream tasks share one stratified image-level split of HyperKvasir: hkv_findings (20-way pathology finding), hkv_category (4-way), hkv_tract (upper vs lower GI), hkv_pathology (pathological vs other), and hkv_seg — zero-shot polyp segmentation by dense patch-feature k-NN label transfer, no training.

The data-pipeline story (Phase 7) — tried, then dropped

GastroNet-5M is ~1 TB of PNGs in 506 gated portal zips — it does not fit LRZ's ~90 GB of writable quota. The original plan was an S3 data lake (versioned bucket, IAM roles, a Glue/Athena catalog, a monthly cost budget) fed by a throwaway EC2 instance in the same region, all declared in Terraform. The infrastructure code is complete and was applied, but the EC2 ingest step failed repeatedly — every instance vanished ~20 minutes after boot, a restriction on the fresh AWS account we could not clear in time. We do not use this path. The permanent solution is curating directly on LRZ: portal_to_wds.py streams one zip at a time, resizes / re-encodes / de-duplicates it into WebDataset .tar shards, then deletes the zip — so the full raw corpus never has to land at once, and the curated tier (~50 GB) fits comfortably on LRZ storage. That is the path that actually produced the tier the SSL runs consume; the AWS S3 lake is dead infrastructure being torn down, not an active dependency.

“Ingest” and “curate”

Two stages of turning the source data into something trainable.

  • Ingest — pull the bytes out of the source system into ours. The source is the Cortex portal, where GastroNet-5M sits as 506 ZIPs (≤10k PNGs each) behind an authenticated API. Per file: POST /api/provided_file/<id>/download_url/ → a 10-minute presigned URL → stream the ZIP to scratch (Range-resume if it expires) → hand it to curation → delete it.
  • Curate — transform those raw files into a clean, uniform, training-ready dataset. For every image: decode (drop if corrupt) → resize the short side to 224 px (downscale only — the model input size) → re-encode JPEG q87 RGB → drop perceptual-hash duplicates (endoscopy video frames repeat heavily) → pack the survivors into .tar shards of ~10k images (the WebDataset format: sequential reads, no per-file open() cost). Result for the subset: 581,518 kept, 268 dropped, 60 shards, 8.1 GB, 155 min — the raw ZIPs were roughly 8× larger.

Why 581k images, not 4.8M

Two independent reasons, and neither is a storage limit:

  • Only 60 of 506 zips are ingested so far — a deliberate time-vs-completeness call for the deadline. 60 zips took 155 min; all 506 would be ~22 h. The backfill is a one-command resume (portal_to_wds.py skips zips already in _ingested.txt) and can run any time; the full curated tier (~50–65 GB) fits LRZ fine.
  • The experiment never trains on the full corpus anyway. config.yaml sets ssl.subset_images: 700000 — the design is a short in-domain adaptation from a strong pretrained init (hence the LLRD 0.75 layer-wise decay), not pretraining from scratch. Full-corpus single-GPU SSL is 10–40 GPU-days per run × 4 runs — infeasible in the time budget. The current runs see 581,518 × 3 epochs ≈ 1.74M image-presentations, squarely in the intended range. “-5M” in the name is the available pool; the run samples from it.

What the baseline says

  • ImageNet init beats SigLIP-2 on every task, on both discrimination (accuracy, NLL) and mostly on calibration. This is the opposite of the pre-registered sanity guess — the web-scale contrastive model was expected to transfer better. For endoscopy k-NN it does not: supervised ImageNet features are more linearly separable here, and their patch tokens carry far more local structure (segmentation Dice 0.67 vs 0.31).
  • hkv_tract is flagged — confirmed structural, not leakage. A dedicated audit (hkv_tract_audit.py) checked the finding ontology directly: 23 of 23 HyperKvasir findings are tract-exclusive (each finding occurs in upper-GI or lower-GI images only, never both), so upper-vs-lower-GI is recoverable from coarse image content almost by construction. Re-run on 2026-09-13 against the deduplicated split, independent of the accuracy number itself. Upper vs lower GI sits at 99.5% accuracy / 0.999 AUROC — near-trivially separable from global image appearance, and with an image-level split (HyperKvasir has no procedure IDs) near-duplicate frames from one procedure can still straddle reference and query. Treated as an interpretation caveat, recorded in every JSON.
  • Temperature scaling is not uniformly helpful. For ImageNet, T > 1 and post-T ECE sometimes rises (findings: .048 → .111): the k-NN “logits” (log of normalised vote mass) are not true logits, and a single scalar fit on a 15% cal split can over-correct. For SigLIP-2 on category / pathology, T < 1 and post-T ECE improves. The pre-vs-post-SSL delta is the intended read, not the absolute value.
  • The 20-way findings task is imbalanced. Balanced accuracy ~0.61 (imagenet) / ~0.50 (siglip2) against raw accuracy ~0.85 — strong on common findings, weak on rare ones, AUROC still ~0.95.

Flag — LeJEPA on the ImageNet init is a genuine, severe failure mode

Query accuracy on hkv_findings collapsed from 82.4% pre-SSL to 19.9% post-SSL (AUROC 0.95 → 0.67); every classification task lost 19–62 accuracy points. This was checked against a pipeline bug and ruled out: the pre-SSL baselines in the same evaluation sweep are normal, the other three settings in the same sweep are normal, and SSL training itself shows no instability — loss fell smoothly (0.044 → 0.033), no non-finite-loss skips, effective rank stayed at 33.9 (healthy; classic collapse reads ~1). AUROC staying above 0.5 confirms the features still carry some signal — k-NN is just badly miscalibrated to the point of being nearly useless at the decision threshold.

Reading: LeJEPA's SIGReg term aggressively reshapes the batch toward an isotropic Gaussian. Applied full-backbone to an already highly class-structured supervised ImageNet embedding, it appears to overwrite that structure faster than the light LLRD 0.75 layer decay can protect it — the representation stays spread out (rank) but loses its linear/k-NN separability. Notably this is worse, not better, than the earlier accidental ~4-epoch run of the same setting (that one only lost 7–12 accuracy points) — a clean, monotonic 3-epoch cosine schedule drifted further from the supervised init than a run whose LR schedule was inadvertently interrupted and restarted. That is itself a data point: the damage accumulates with clean optimisation, it is not an artefact of the earlier bug.

The story across all four settings

  • DINO is the reliable adapter. It improved calibration and/or segmentation from both initialisations, with no accuracy cost anywhere. From SigLIP-2 the gains are large (ECE −0.01 to −0.06, seg Dice +0.40); from the already-strong ImageNet init they are smaller but still net positive (findings improves on every axis at once).
  • LeJEPA is powerful but init-sensitive. From SigLIP-2 (room to improve) it trades accuracy for markedly better calibration and a strong segmentation gain (+0.13 Dice). From ImageNet (already excellent) it is destructive — the aggressive SIGReg regulariser has nothing to gain and a great deal to lose.
  • hkv_findings and segmentation are where SSL matters most for the three well-behaved settings; the near-saturated hkv_tract / hkv_pathology tasks barely move either way.
  • Practical takeaway: if the deployment init is a strong supervised backbone, prefer a gentle self-distillation objective (DINO) for in-domain adaptation; reserve an aggressive distributional regulariser (LeJEPA) for weaker / less task-aligned starting points, or pair it with a much smaller LR / shorter schedule / stronger LLRD when starting from a strong supervised init.

Layer · models

Every initialisation — SigLIP-2, ImageNet, or an SSL checkpoint — is funnelled into one timm VisionTransformer and exposed through an identical feature API, so the k-NN / calibration code never knows which backbone it holds.

vlfz/models/vit_backbone.py134 LOC Backbone-agnostic ViT-B/16 factory + uniform feature API. ★ flagship

The pooling choice is the crux: feature(x) is a non-parametric LayerNorm of the mean patch token. That erases the difference between SigLIP-2 (no CLS token, GAP head) and ImageNet ViT (CLS token) — the same 768-d vector for every init, and a stable SSL target.

28class ViTBackbone(nn.Module):
29    def __init__(self, trunk, init):
33        self.num_prefix = int(getattr(trunk, "num_prefix_tokens", 0))
34        self.embed_dim  = int(getattr(trunk, "embed_dim", 768))
42    def forward_tokens(self, x):
43        t = self.trunk.forward_features(x)            # (B, T, C)
46        return t[:, self.num_prefix:, :]              # drop cls/reg prefix
48    def feature(self, x):
49        patch  = self.forward_tokens(x)               # (B, N, C)
50        pooled = patch.mean(dim=1)                    # (B, C)
51        return F.layer_norm(pooled, (pooled.shape[-1],))   # non-affine
  • L33–34 Read num_prefix_tokens and embed_dim from the trunk itself — 1 prefix token for ImageNet (CLS), 0 for SigLIP-2-GAP.
  • L42–46 forward_tokens returns the post-trunk patch grid with the prefix sliced off — 196 tokens at 224 px, used directly by segmentation.
  • L48–51 feature = mean-pool + non-affine LayerNorm. No learned parameters, so it is identical pre- and post-SSL and across inits.

PART 5
Case study

The LR = 0 bug

The first full-scale SSL job started on an A100 the morning of 2026-09-08. Watching its TensorBoard scalars caught something the smoke tests could not: it was not training at all.

Symptom

lr flat at 0.000e+00 at steps 49, 5349, 10649. loss flat at 0.737 over 10,000+ steps. loss/var pinned at the variance-hinge floor. Zero checkpoints in the run directory.

Two independent bugs compounded:

  1. trainer.global_step never advanced. training_step called opt.optimizer.step() — the raw AdamW.step() — instead of opt.step() (the Lightning optimizer). That bypass was a workaround for an intermittent CPU hang on the login node, but on GPU it means Lightning's step counter stays at 0. Consequences: cosine_lr(global_step=0, …) sits at warmup-step-0, i.e. LR ≡ 0, so every optimizer step is a no-op; and ModelCheckpoint(every_n_train_steps=500) also keys off global_step, so no last.ckpt was ever written — a self-resubmit would have restarted from scratch, forever.
  2. The WebDataset epoch was 12× too long. .with_epoch(4687) was applied to the per-worker pipeline, so with num_workers=12 a Lightning “epoch” was ~56,000 batches (~5 h). The other checkpoint path, on_train_epoch_end, would not have fired inside the 6-hour wall either.

Together: the run could produce nothing usable and loop indefinitely.

Fix — commit ccb8985

1. opt.step() on CUDA (raw bypass kept only for CPU smokes) → global_step advances, schedules and checkpoint triggers work.

2. .with_epoch() moved onto a wds.WebLoader wrapping the DataLoader, applied after the worker fan-in → exactly steps_per_epoch batches per epoch. Verified on the login node: request 40, get 40, stable across epochs at num_workers=4.

The GPU smoke had passed because 4 steps at batch-size 2 is entirely inside LR warmup — LR is ~0 there whether or not the counter moves, and the smoke only checks that a checkpoint file appears and resume works, which the epoch-end path did handle. The bug only shows up at scale, which is exactly why the run was being watched.
