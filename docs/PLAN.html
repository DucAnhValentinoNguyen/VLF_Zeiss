CONTEXT

Why this plan exists

The published 4-setting result (2026-09-12/13) trained on a 60-shard / 581k-image subset (12% of GastroNet-5M) and found ImageNet beating SigLIP-2 on every HyperKvasir task pre-SSL, with LeJEPA/ImageNet regressing severely post-SSL. Two decisions came out of reviewing that: drop SigLIP-2 entirely — matching a teammate's (lilian70nn/Endoscopy) pipeline for a fairer comparison — and require training on the full corpus, not a subset. The end goal changed too: this isn't a comparison exercise anymore. Whichever setting wins gets promoted to a "foundation model" checkpoint that further downstream fine-tuning will build on.

DECISIONS

What was asked, and why

Two things were investigated before committing to an approach, rather than assumed.

Multi-GPU (--gres=gpu:2 or :4) — investigated, not pursued yet

Finding

The data loader is already DDP-safe (nodesplitter=wds.split_by_node, workersplitter=wds.split_by_worker, gastronet.py:208-209), and SSLModule accesses self.backbone/self.head directly with no .module indirection issues. But two real correctness traps exist and are unsolved today:

  • DINO's update_center() batch-means the teacher output locally. Under DDP, each rank would silently drift to a different centering value with no dist.all_reduce anywhere in the code — a silent bug, not a crash.
  • LeJEPA's SIGReg term is a batch-distribution statistic. 4 ranks at bs=128 each is 4 independent noisy estimates, not one estimate on an effective bs=512 — changes what the regularizer does, not just its speed.

Decision: stay single-GPU. Remove the one free inefficiency (grad checkpointing, below) first, measure, and only revisit DDP as its own sub-project if throughput is still the bottleneck.

GastroNet-5M EDA — deferred

Finding

Only 69/506 zips are ingested locally right now (~669k of ~4.9M images). The reference paper link provided was a presigned S3 URL that had already expired (5-minute TTL) by fetch time.

Decision: one complete EDA pass after the full ingest finishes, not a partial pass now redone later. pipeline/dq/checks.py (corrupt %, phash dup-cluster %, dimension/RGB histograms) is already written for this and unrun — it becomes the base for a new artifact page once the corpus is fully in, folding in the paper's documented quirks once a durable link is available.

I
The actual goal

Model selection & checkpoint promotion

Everything above exists to produce one thing: a checkpoint worth calling a foundation model. That reframes what matters about it — from "one row in a comparison table" to "a durable asset something else depends on."

Selection metric

A model meant for further fine-tuning is judged on transferable representation quality, not frozen-feature calibration — fine-tuning recalibrates anyway. Primary criterion: mean post-SSL balanced-accuracy across the 4 classification tasks + Dice on hkv_seg. ECE/NLL and the collapse/effective_rank W&B curve are a gate, not the ranking — a candidate that regressed vs. its own pre-SSL baseline, or whose effective rank collapsed (this benchmark's own precedent: the earlier LeJEPA/ImageNet run lost 19–62 accuracy points on the subset; watch for a repeat on the full corpus), is disqualified regardless of any other number. With SigLIP-2 dropped this is a straight DINO-vs-LeJEPA call.

Promotion, not just "keep the file"

save_eval_backbone() already writes ema_backbone.pt per setting, but nothing marks one as the model or protects it from the per-setting cleanup logic that auto-deletes resume checkpoints on finished runs. Once both settings finish: copy the winner to a separate $OUT_ROOT/foundation_model/ema_backbone.pt, with a CARD.json recording which setting won, both settings' metric values (so the decision stays auditable), corpus size, epoch/step count, git SHA, date.

Don't let it depend on LRZ scratch's reliability

Given the exact failure mode this week (LRZ_DSS06 stuck at its quota cap; a crash loop that nearly clobbered checkpoints), the one file everything downstream depends on shouldn't live only on that storage. W&B is already wired up (_wandb_logger) — log the winning ema_backbone.pt as a versioned W&B Artifact at promotion time. A few lines (wandb.Artifact(...).add_file(...)), and the checkpoint becomes durable and decoupled from LRZ storage entirely.

Downstream fine-tuning tasks themselves are explicitly out of scope for this plan — it stops at a promoted, documented, durably-stored checkpoint ready for that next phase.

VERIFY

How each phase is checked

  • python -m pytest -q green after the init-loop narrowing.
  • A GRAD_CKPT=0 timed smoke shows it/s ≥ the current measured floor (3.79 LeJEPA / 1.07 DINO) before trusting it for the epoch-budget calculation.
  • resampled=False smoke: one full local pass over the 69 currently-ingested shards, every shard visited exactly once (a log line per shard boundary), no worker hangs.
  • Storage: a live write test (dd) re-checked after cleanup and after any LRZ-side fix — never assumed from the dashboard banner alone (the 2026-09-14 lesson).
  • Post full-ingest: _ingested.txt line count == 506 (or 506 minus a documented _failed.txt remainder); curated tier ~68 GB.
  • Final SSL artifacts: both ema_backbone.pt report the expected gstep; W&B shows both runs with loss / collapse/effective_rank curves, no non-finite-loss skips.
  • Foundation model: foundation_model/ema_backbone.pt + CARD.json exist, the card's winning metrics match report.md, and the same file resolves as a W&B Artifact from a clean shell — i.e. it survives LRZ storage being unavailable.
